--------------------------------------------------------------------------------
LESSONS FROM IMPORT PHASE
--------------------------------------------------------------------------------

- The Import Flat File wizard can silently drop values during type
  conversion. Always read the warning and reconcile control totals
  (row count + SUMs) with the source after import.

- Row-by-row UPDATE is fine for 1 row but not scalable. For larger
  files: load into a staging table with all columns as text, find
  bad values using TRY_CAST / TRY_CONVERT, build final table in one
  INSERT ... SELECT, then match control totals with source.

ISSUE 3 — Float Precision Broke Discount Comparisons
--------------------------------------------------------------------------------

Problem identified:
    Stored float value:   0.200000002980232  (CSV -> wizard -> float)
    Literal 0.2 in query: 0.200000000000000  (SQL decimal -> float)
    Because 0.200000002980232 > 0.200000000000000:
      - WHERE Discount = 0.2 returned 0 rows
      - CASE bucket "WHEN Discount <= 0.2" would push 20% rows into
        the 21-40% band and silently distort discount-band analysis

Future impact (if unfixed):
    Expected: 20% discount -> "2) 1-20%" band
    Actual:   20% discount -> "3) 21-40%" band  (WRONG)

Fix procedure:
    USE SuperstoreDB;
    GO

    -- STEP 1: Backup
    SELECT * INTO superstore_backup_before_discount_fix FROM superstore;

    -- STEP 2: Before snapshot
    SELECT ROUND(Discount, 2) AS Disc, COUNT(*) AS Lines
    FROM superstore GROUP BY ROUND(Discount, 2) ORDER BY Disc;

    -- STEP 3: The fix
    ALTER TABLE superstore ALTER COLUMN Discount decimal(3,2) NOT NULL;

    -- STEP 4: After check
    SELECT Discount, COUNT(*) AS Lines
    FROM superstore GROUP BY Discount ORDER BY Discount;

    SELECT COUNT(*) AS Exactly_0_2_After_Fix
    FROM superstore WHERE Discount = 0.2;

    -- STEP 5: Control totals (must match baseline)
    SELECT ROUND(SUM(Sales), 2)  AS Total_Sales,
           ROUND(SUM(Profit), 2) AS Total_Profit,
           COUNT(*)              AS Total_Rows
    FROM superstore;

Results after fix:
    Exactly_0_2_After_Fix = 3,657
    Total_Sales           = 2,297,200.86   (unchanged)
    Total_Profit          = 286,397.02     (unchanged)
    Total_Rows            = 9,994          (unchanged)

Screenshot: 02_data_checks_float_to_decimal_fix.png

Decision:
    Only Discount converted to decimal(3,2). Sales and Profit kept
    as float because they are always shown with ROUND and noise is
    < 1 cent. Control totals match to the cent.

Lesson:
    The wizard picked float by default. NEVER use float for exact
    comparisons — discounts, tax rates, currency thresholds.
    Rule of thumb: float for science, decimal for money and
    percentages. For "discount > 20%" style business rules, float
    creates silent logic bugs.

STEP 18 — Reusable View Creation (v_superstore) + Disc_Band Validation
--------------------------------------------------------------------------------

1. Kya kiya:
   Analysis-ready view create kiya jisme base table ke saare columns (*)
   ke saath 2 derived columns add kiye:
   - Ship_Days: DATEDIFF(day, Order_Date, Ship_Date)
   - Disc_Band: CASE-based discount bucketing
     '1) 0%' | '2) 1-20%' | '3) 21-40%' | '4) >40%'

   Note: View intentionally minimal rakha — sirf wahi derived columns
   jo downstream queries (Q4, Q10) actually consume karte hain.
   Baaki calculations (YoY, MoM, Margin%) query-level pe inline hain
   taaki view lean aur maintainable rahe.

   CREATE OR ALTER VIEW v_superstore AS
   SELECT *,
     DATEDIFF(day, Order_Date, Ship_Date) AS Ship_Days,
     CASE WHEN Discount = 0        THEN '1) 0%'
          WHEN Discount <= 0.2     THEN '2) 1-20%'
          WHEN Discount <= 0.4     THEN '3) 21-40%'
          ELSE '4) >40%' END AS Disc_Band
   FROM superstore;

   Uske baad view-level Disc_Band distribution ko Excel pivot se
   cross-verify kiya (Check 17f):

   SELECT Disc_Band, COUNT(*) AS Lines,
          ROUND(SUM(Sales),0) AS Sales, ROUND(SUM(Profit),0) AS Profit,
          ROUND(SUM(Profit)*100.0/SUM(Sales),1) AS Margin_Pct
   FROM v_superstore GROUP BY Disc_Band ORDER BY Disc_Band;

2. Kya finding aayi:
   View baseline:
   - View_Rows   = 9,994           ✅ (base table se match)
   - View_Sales  = $2,297,200.86   ✅ (Check 17 se match)
   - View_Profit = $286,397.02     ✅ (Check 17 se match)

   Disc_Band distribution (v_superstore vs Excel pivot) — MATCHED ✅

   | Disc_Band | Lines | Sales      | Profit    | Margin_Pct |
   |-----------|-------|------------|-----------|------------|
   | 1) 0%     | 4,798 | 1,087,908  |  320,988  |  +29.5%    |
   | 2) 1-20%  | 3,803 |   846,522  |  100,785  |  +11.9%    |
   | 3) 21-40% |   460 |   234,138  |  -35,817  |  -15.3%    |
   | 4) >40%   |   933 |   128,632  |  -99,559  |  -77.4%    |
   | TOTAL    | 9,994 | 2,297,200  |  286,397  |            |

   Key signal (preview of Q4):
   - Margin positive at 0% and 1-20% bands
   - Margin turns NEGATIVE from 21-40% band onward
   - >40% band alone: 933 lines, -$99,559 profit, -77.4% margin
   - Band line counts add to 9,994; consistent with post-fix

  1,894 rows / 1,862 keys → NOT UNIQUE ❌
  32 Product_IDs carry two different Product_Names (1,894 − 1,862 = 32).
  Screenshot: 06_key_check_product_key.png

CHECK 20b — Dim_Product composite key (Product_ID | Product_Name):
  1,894 rows / 1,894 keys → UNIQUE ✅
  Screenshot: 06_key_check_productId_productName.png

CHECK 20c — Which Product_IDs have multiple names:
  32 Product_IDs returned with COUNT(DISTINCT Product_Name) > 1.
  Root cause: likely product name changes over 4 years for same SKU.

CHECK 21 — Postal Code cardinality:
  631 distinct Postal_Codes in the dataset.
  Screenshot: 06_key_check_postal.png

CHECK 22 — Dim_Location composite key (Postal_Code - City):
  632 rows / 632 keys → UNIQUE ✅
  631 postal codes but 632 combinations → exactly one postal code is
  shared by two different cities.
  Screenshot: 06_key_check_location.png

Decisions:
  D1. Dim_Product will use composite key: Product_Key = Product_ID | Product_Name
  D2. Dim_Location will use composite key: Location_Key = Postal_Code - City
  D3. Both composite keys must be added as calculated columns in the
      v_superstore fact table before building relationships in Power BI.
  D4. Dim_Customer can use Customer_ID directly (already unique).

Lesson: NEVER assume a business ID is unique. Always run
  COUNT(*) vs COUNT(DISTINCT key) before creating a 1-to-Many relationship.
  A duplicate key on the "one" side causes ambiguous filter propagation
  and silently wrong DAX totals.
